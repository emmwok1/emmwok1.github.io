Featured project

What did our monitoring see when I attacked it?

A client-style SOC engagement through the Amdari programme, for a company I can't name. The brief was to get Windows, network and Linux logs into one Splunk server, then find out whether the monitoring would notice an attacker. I tested it myself with one Nmap scan and two failed SSH logins as a user that does not exist, then compared what each log source recorded.

Splunk EnterpriseUniversal ForwarderSysmonSuricataLinux auth logsMITRE ATT&CK
02:44 Sysmon nmap.exe connects to port 22 (scan starts) 02:45 Suricata ALERT ET SCAN Potential SSH Scan 02:45 Linux log connection resets from the scanner 03:09 Sysmon ssh.exe connects to port 22 03:11 Linux log Invalid user testuser 03:26 Sysmon ssh.exe connects to port 22 03:26 Linux log Invalid user testuser Suricata no alert for either login

What I found

  • Suricata flagged the scan and said nothing about the failed logins. SSH is encrypted, so the likely reason is that it sees the connection but not the result. I have not tested that yet.
  • The Linux log was the only source that recorded the failed login step.
  • Sysmon tied both back to the exact programs on my laptop.

What I built and fixed

  • Two alerts that fired during the test: Invalid SSH attempt and Failed Windows logon (event 4625).
  • A three-panel dashboard for logons and Suricata alerts.
  • Fixed a forwarder that could not read Sysmon (Access Denied) by adding its service account to the Event Log Readers group.
  • Mapped the activity to MITRE ATT&CK: T1595, T1046 and T1133.

Recommendation: network monitoring alone is not enough. Host logs catch what the network cannot see. Still open: why Windows left the account name blank on the failed logons. I would rather list it than guess.

Vulnerability management lab: scan, patch, prove it

Completed 13 November 2026

Ran the full vulnerability management cycle on a shared web server running nginx 1.15.5, inside the scope I was given (nginx, port 80 only). I scanned with OpenVAS, ranked the findings by CVSS, upgraded nginx to 1.30.4 with an Ansible playbook, and re-scanned to prove the fix. I ran and verified the lab's playbooks and explained what each stage does.

22 → 13scan results
4 → 0High findings
4 → 0Medium findings
1.15.5 → 1.30.4nginx version

What I did

  • Wrote up the top seven findings by CVSS with CVE numbers and a plain-language "what an attacker could do" line for each. The top one scored 7.8 (CVE-2022-41741 and CVE-2022-41742, a crafted MP4 that can crash a worker).
  • Patched with an Ansible playbook that backs up the old binary, tests the new one against the config, and restores the backup automatically if anything fails.
  • Delivered a four-page report with appendices: baseline and re-scan reports, playbooks and evidence.

What I learned

  • The nginx findings were version-based with a quality-of-detection of 30%, so the default view hid them until I set the filter to show everything. I noted that several may be false positives, since they need optional modules.
  • Another user rolled the shared server back before my re-scan, so my first re-scan still showed the old results. I proved it with the version and file timestamps, told the group, re-patched and re-scanned.
  • Verify the state of a target before and after every change.
